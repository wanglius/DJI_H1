# A 板 ↔ B 板 串口通信协议（客户开发参考版）V1.0

> **适用范围**：A 板 = PSDK 控制板（STM32F407），B 板 = 客户采集板。
> 本文供 B 板开发方参考实现，只列协议与交互逻辑，不含 A 板内部实现说明。

---

## 1. 串口参数

| 项目 | 参数 |
|---|---|
| 连接器 | GH1.25-4P：3V3 / TX / RX / GND |
| 电平 | 3.3V TTL |
| 波特率 | 115200 |
| 数据格式 | 8 数据位 / 无校验 / 1 停止位（8N1） |
| 流控 | 无 |
| 字节序 | **小端（Little-Endian）**，含 CRC |

## 2. 帧格式

所有报文统一使用下列帧格式，最小 7 字节：

```
+------+------+-----+-----+-----+----------+-------+
| 0xAA | 0x55 | LEN | CMD | SEQ | PAYLOAD  | CRC16 |
|  1B  |  1B  | 1B  | 1B  | 1B  | 0~247B   |  2B   |
+------+------+-----+-----+-----+----------+-------+
```

| 字段 | 说明 |
|---|---|
| HEAD | 固定 `0xAA 0x55` |
| LEN | PAYLOAD 字节数 |
| CMD | 命令字，见第 3 节 |
| SEQ | 序号 0~255 循环。发送方自增；应答方原样带回；**重发沿用原 SEQ** |
| CRC16 | CRC16-CCITT-FALSE，校验范围 **LEN + CMD + SEQ + PAYLOAD**（不含帧头），**低字节先发** |

### 2.1 CRC16 算法

```c
/* CRC16-CCITT-FALSE: poly=0x1021, init=0xFFFF, 不反转, xorout=0x0000 */
uint16_t crc16_ccitt(const uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc ^= (uint16_t)(*data++) << 8;
        for (uint8_t i = 0; i < 8; i++)
            crc = (crc & 0x8000) ? ((crc << 1) ^ 0x1021) : (crc << 1);
    }
    return crc;
}
```

**初步设定：**

| 测试项 | 输入 | 期望结果 |
|---|---|---|
| 算法自检 | ASCII `"123456789"` | CRC = **`0x29B1`** |
| 整帧样例 | `0x30` 准备断电，`grace_sec=10`，SEQ=7 | 上线字节流 = **`AA 55 01 30 07 0A 0C 0F`** |

> 注意整帧样例中 CRC 为 `0x0F0C`，线路上是 `0C 0F`（低字节在前）。

### 2.2 收发要求

- CRC 错误丢弃整帧，不请求重传（周期帧丢一帧无影响）。
- 帧内字节停顿超过 100ms 视为帧断裂，重新同步。
- 逐字段按小端显式编解码。

## 3. 命令字总表

| CMD | 方向 | 名称 | 周期 | 需应答 |
|---|---|---|---|---|
| `0x20` | A → B | 握手请求 | 未建链时 1Hz | 是（`0xA0`） |
| `0xA0` | B → A | 握手应答 | 响应式 | — |
| `0x01` | A → B | 实时数据帧 | 5Hz | 否 |
| `0x10` | A → B | 开始拍照 | 事件 | 是（`0x90`） |
| `0x11` | A → B | 停止拍照 | 事件 | 是（`0x90`） |
| `0x30` | A → B | 准备断电 | 事件 | 是（`0x90`） |
| `0x81` | B → A | 状态上报 | 1Hz | 否 |
| `0x90` | B → A | 通用应答 | 响应式 | — |

## 4. 报文定义

### 4.1 `0x20` 握手请求（A → B）— 36 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | proto_ver | 协议版本，当前 `0x01` |
| 1 | uint8 | drone_link | 0 = 未连上飞机，1 = 与飞行器链路正常 |
| 2 | uint16 | a_fw_ver | A 板固件版本 |
| 4 | char[32] | drone_sn | 无人机序列号，ASCII，不足补 `0x00` |

> **SN 为 32 字节，满 32 字符时无结束符**，请按"最多 32 字符"处理，不要直接当 C 字符串使用。
> A 板未建链时按 1Hz 重发握手，每次携带同一 SN；若首次握手时飞机链路尚未建立（SN 为空、`drone_link = 0`），A 板取得 SN 后会主动补发一帧。

### 4.2 `0xA0` 握手应答（B → A）— 5 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | proto_ver | B 板支持的协议版本 |
| 1 | uint8 | b_ready | 0 = 初始化中，1 = 就绪可拍照 |
| 2 | uint16 | b_fw_ver | B 板固件版本 |
| 4 | uint8 | request_seq | **被应答的 `0x20` 帧 SEQ，原样回显** |

### 4.3 `0x01` 实时数据帧（A → B，5Hz）— 30 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | int32 | latitude | 纬度，**单位 1e-7 度**，北纬为正 |
| 4 | int32 | longitude | 经度，**单位 1e-7 度**，东经为正 |
| 8 | int32 | alt_rel | 相对起飞点高度，**毫米** |
| 12 | uint32 | utc_sec | UTC 秒（Unix 时间戳） |
| 16 | uint32 | mono_ms | A 板单调毫秒计数，自上电递增 |
| 20 | uint16 | utc_msec | 毫秒 0~999 |
| 22 | uint8 | src_flags | 数据来源标志，见 4.3.1 |
| 23 | uint8 | gps_fix | GPS 定位状态，见 4.3.2 |
| 24 | uint8 | rtk_solution | RTK 解算状态，见 4.3.3 |
| 25 | uint8 | flight_status | 0 = 电机停止，1 = 地面电机转动，2 = 空中 |
| 26 | uint8 | display_mode | 飞行模式，见 4.3.4 |
| 27 | uint8 | battery_pct | 电池剩余百分比 0~100 |
| 28 | uint8 | a_status | A 板状态位，见 4.3.5 |
| 29 | uint8 | valid_flags | 有效性标志，见 4.3.6 |

> 经纬度换算：实际度数 = 字段值 × 1e-7。例：`1163974280` → 116.3974280°。

#### 4.3.1 `src_flags` —— 数据来源标志

| bit | 含义 |
|---|---|
| 0 | **经纬度来源**：0 = GPS，1 = RTK |
| 1 | **相对高度来源**：0 = GPS，1 = RTK |
| 2~7 | 保留 |

> ⚠ **同一帧内经纬度与高度可能来自不同来源，必须分别读取 bit0 与 bit1，不能用单一标志推断两者。**
>
> 典型情形：起飞时 RTK 未固定，升空后 RTK 恢复固定——此时经纬度切换为 RTK（厘米级），而相对高度因起飞点没有 RTK 基准，本架次将始终使用 GPS。

#### 4.3.2 `gps_fix` —— GPS 定位状态

| 值 | 含义 |
|---|---|
| 0 | 无定位 |
| 1 | 仅航位推算 |
| 2 | 2D 定位 |
| 3 | 3D 定位 |
| 4 | GPS + 航位推算 |
| 5 | 仅授时 |

#### 4.3.3 `rtk_solution` —— RTK 解算状态（取值不连续）

| 值 | 含义 | 精度量级 |
|---|---|---|
| 0 | 不可用 | — |
| 1, 2, 8, 19, 20 | 其他状态 | — |
| 16 | 单点解 | 米级 |
| 17, 18 | 差分解 | 亚米级 |
| 32, 33, 34 | 浮点解 | 分米~米级 |
| 48 | L1 整数解 | 分米级 |
| 49 | 宽巷整数解 | 分米级 |
| **50** | **固定解** |

> **本系统只把 `50` 视为 RTK 固定解**，其余取值一律按未固定处理、使用 GPS 数据。

#### 4.3.4 `display_mode` —— 飞行模式（常用取值）

| 值 | 含义 |
|---|---|
| 11 | 自动起飞 |
| 12 | 自动降落 |
| 15 | 返航 |
| 33 | 强制降落 |

其余取值为飞行器其他工作模式，B 板可按需忽略。

#### 4.3.5 `a_status` —— A 板状态位

| bit | 含义 |
|---|---|
| 0 | 与飞行器链路正常 |
| 1 | 自定义控件注册成功 |
| 2 | 数据订阅正常 |
| 3 | 起飞点基准已锁存 |
| 4 | RTK 起飞高度基准有效 |
| 5~7 | 保留 |

> A 板的详细错误信息输出到其调试串口，不通过本协议上报。本字节用于让 B 板判断"当前这一帧是否可信"。

#### 4.3.6 `valid_flags` —— 有效性标志

| bit | 含义 |
|---|---|
| 0 | 经纬度有效 |
| 1 | 相对高度有效 |
| 2 | UTC 时间有效 |
| 3 | 电量数据有效 |
| 4~7 | 保留 |

> **有效位为 0 时，对应字段内容不可用，请勿记录或参与计算。**
> 有效位同时包含"数值合理"与"数据新鲜"两重含义：相关数据源超过 1 秒未更新时，即使数值看起来正常，A 板也会将该位清零。
>
> 注意 bit0 与 bit1 是独立的：2D 定位状态下经纬度可用而高度不可用，此时 bit0 = 1、bit1 = 0。

#### 4.3.7 时间戳使用说明

| 字段 | 用途 | 精度 |
|---|---|---|
| `utc_sec` + `utc_msec` | **绝对时间基准** | 约 **±100~200ms** |
| `mono_ms` | **帧间相对时序** | **毫秒级** |

- 本系统不使用 PPS 硬件同步，**请勿基于 `utc_sec`/`utc_msec` 做亚秒级精确对齐**。
- 需要高精度相对时序时请使用 `mono_ms`；它自 A 板上电起单调递增，不受 UTC 更新影响。
- `mono_ms` 为 uint32 毫秒，**做差值时按无符号回绕处理**。
- `mono_ms` 对应的是本帧所采用的那份经纬度样本的采样时刻；同帧内高度、状态、电量取各自最近一次更新值，与之可能相差最多一个数据周期。

### 4.4 `0x10` 开始拍照（A → B）— 6 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | trigger_src | 固定为 `1` |
| 1 | uint8 | rsv | 保留，填 0 |
| 2 | uint32 | session_id | 本架次任务编号，见 4.9 |

### 4.5 `0x11` 停止拍照（A → B）— 6 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | reason | 停止原因，见下表 |
| 1 | uint8 | rsv | 保留，填 0 |
| 2 | uint32 | session_id | 与对应的 `0x10` 一致 |

| reason | 含义 |
|---|---|
| 1 | 正常结束（控件置关） |
| 2 | 返航 |
| 3 | 低电量返航 |
| 4 | 自动降落 |
| 5 | 已落地 |
| 6 | 手动中止任务 |
| 7 | 与飞行器链路断开 |
| 8 | 准备断电 |

### 4.6 `0x30` 准备断电（A → B）— 1 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | grace_sec | A 板将在 N 秒后切断 B 板 5V 供电 |

> **B 板收到本帧后应立即停止写入并完成落盘**，随后在 `0x81` 中把 `safe_power_off` 置 1。
> A 板在收到 `safe_power_off = 1` 或 `grace_sec` 超时后切断供电。

### 4.7 `0x81` 状态上报（B → A，1Hz）— 14 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | b_state | 0 = 初始化，1 = 就绪，2 = 故障 |
| 1 | uint8 | actual_capture | **0 = 未拍照，1 = 拍照中。B 板实际状态** |
| 2 | uint8 | err_code | 0 = 无故障，其余由 B 板定义 |
| 3 | uint8 | storage_free_pct | 剩余存储百分比 0~100 |
| 4 | uint32 | frame_count | 本架次已采集帧数 |
| 8 | uint32 | session_id | 当前任务编号，无任务填 0 |
| 12 | uint8 | safe_power_off | 0 = 不可断电，1 = 已落盘可断电 |
| 13 | uint8 | rsv | 保留 |

> **本帧同时作为 B 板心跳，必须按 1Hz 持续发送**，即使处于空闲状态。
> `actual_capture` 是 A 板判断拍照状态的唯一权威依据，也会回显到遥控器上的控件显示。

### 4.8 `0x90` 通用应答（B → A）— 3 字节

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint8 | ack_cmd | 被应答的命令字 |
| 1 | uint8 | ack_seq | 被应答帧的 SEQ |
| 2 | uint8 | result | 0 = 成功，1 = 失败，2 = 忙，3 = 参数错误，4 = 状态不允许 |

`0x10` / `0x11` / `0x30` 三条指令**必须应答**。

### 4.9 `session_id`

由 A 板生成，格式为 `(上电标识 << 16) | 任务序号`。B 板只需原样比对与记录，不需解析其含义。同一架次内的 `0x10`、`0x11` 与 `0x81` 使用同一值。

## 5. 交互流程

### 5.1 建链

```
A 板上电 → 给 B 板供电 → 等待 B 板启动
   → A 板每 1s 发送 0x20 握手请求
   → B 板回 0xA0（b_ready = 1，request_seq 回显请求的 SEQ）
   → 建链完成，A 板开始 5Hz 发送 0x01
```

- B 板初始化未完成时可先回 `0xA0` 且 `b_ready = 0`，A 板会继续重试。
- 建链完成后 B 板须开始按 1Hz 发送 `0x81`。

### 5.2 拍照触发

拍照由飞行器航线动作自动触发（客户在 DJI Pilot 2 中给航点挂载「拍照控制」控件动作），也可由操作员在遥控器上手动开关。B 板只需响应 `0x10` / `0x11`。

```
到达起始航点 → A 板发 0x10 → B 板开始采集并回 0x90
飞行途中     → A 板持续 5Hz 发 0x01
到达结束航点 → A 板发 0x11 → B 板停止采集并回 0x90
```

**以下情况 A 板会无条件发送 `0x11`**：返航、低电量返航、自动降落、已落地、手动中止任务、与飞行器链路断开、准备断电。

> **`0x01` 实时数据帧在建链后持续发送，不随拍照开关启停。** 未拍照时同样发送，B 板可按需忽略或用于维护时间基准。

### 5.3 应答与重发

| 项目 | 规则 |
|---|---|
| 应答超时 | A 板发出需应答指令后 200ms 未收到 `0x90` 即重发，最多 3 次 |
| 重发标识 | **重发使用原 CMD 与原 SEQ**，B 板可据此识别 |
| 心跳超时 | A 板连续 3 秒未收到 `0x81` 判定 B 板掉线，转入 1Hz 握手重连 |

### 5.4 B 板需要实现

| 级别 | 规则 |
|---|---|
| **帧级** | 收到与上一条 **CMD 相同且 SEQ 相同**的帧，视为重发：只回 `0x90`，**不重复执行** |
| **会话级** | 收到 `0x10` 时，若 `session_id` 与当前任务相同且**已处于拍照中**，则**无论 SEQ 是否变化**，一律回 `0x90(result=0)` 并保持现状，目标任务已停止则直接回成功 |

> B 板掉线重连后，A 板会用**新的 SEQ** 重发同一 `session_id` 的 `0x10` 来同步状态（见 5.5）。

### 5.5 断线重连后的状态同步

B 板重连成功（A 板重新收到 `0xA0`）后，A 板会**按当前应有的拍照状态主动补发一次**。

A 板还会持续比对拍照状态与自身目标状态，不一致超过 3 秒会重发指令。**B 板需要保证拍照状态和实际情况相符。
